# Slangcart — SIM-binding readiness module

Delivered Oct 2026. Owner decisions on record: native Kotlin SIM module,
Truecaller one-tap number verification, **enforce chat immediately**, gate
**all customer–vendor and support chats**, and **QR device linking** for the
website.

---

## 1. Framework and architecture audit

| Area | Finding |
|---|---|
| Android framework | **Expo managed (SDK 54, React Native 0.81)**. No `android/` directory is committed; the native project is generated by `expo prebuild` inside the Publish/build pipeline. Only `android/keystores` and `android/proguard-rules.pro` exist in the repo. |
| Least-disruptive native route | A **local Expo module** (`frontend/modules/sim-binding`), autolinked at build time. No framework replacement, no ejection, no change to any existing native config. |
| Auth | JWT access + refresh with server-side session registry (`core/security.py`: `get_current_user`, `require_admin`, `register_session`, `rotate_session`). Sessions are revocable, so a stale token cannot outlive a revocation. |
| Existing number verification | **None.** `users.phone` is self-entered and never proven. Registration/login is email + password or Google. This is why "SIM present" could not be allowed to imply "number owned". |
| Backend | FastAPI + Motor/MongoDB, routers mounted under `/api` in `server.py`, rate limiting via `core/rate_limit.py` (slowapi), audit precedent in `security_events` / `push_log`. |
| Chat | `routes/chat.py` — ~30 REST endpoints plus `/api/ws/chat` WebSocket for delivery. Threads in `chat_threads`, messages in `chat_messages`. |
| Target SDK / build | `compileSdk`/`targetSdk` 35, `minSdk` 24, AGP 8.x (Expo default), R8 enabled Oct 2026. |
| Existing permissions | Camera, media images, location (incl. background), foreground service, biometric, notifications. **No phone, SMS or call-log permission existed before this work.** |
| Device attestation already present | `core/play_integrity.py` + `POST /api/security/integrity-report` (dormant until the Play Integrity service account is configured) — the natural place to strengthen anti-tamper later. |

## 2. What was built

### 2.1 Native Android module — `frontend/modules/sim-binding`

`SimBindingModule.kt` uses only Android framework telephony APIs:

* `PackageManager.FEATURE_TELEPHONY` → `DEVICE_UNSUPPORTED` on tablets / Wi-Fi-only hardware.
* `TelephonyManager.simState` → honest `SIM_ABSENT` even without any permission.
* `SubscriptionManager.getActiveSubscriptionInfoList()` → active subscription count (dual-SIM), `isEmbedded` → eSIM (API 29+), `isNetworkRoaming` → roaming.
* `mccString` / `mncString` (API 29+, with the pre-29 fallback) → **public carrier network codes only**.
* `OnSubscriptionsChangedListener` → SIM insert/removal/eSIM switch raises an event, and the JS layer re-verifies immediately. The app also re-checks on foreground resume (throttled to once a minute).

Returned states: `SIM_PRESENT`, `SIM_ABSENT`, `SIM_STATE_UNKNOWN`,
`PERMISSION_DENIED`, `DEVICE_UNSUPPORTED`, `REVALIDATION_REQUIRED`.

Explicitly **not** read: IMEI, IMSI, ICCID, SIM serial, subscription id, the
SIM's own MSISDN. No SMS permission is held, so no SMS can be read or sent.
`SecurityException` (OEM builds that refuse enumeration even when granted) is
caught and reported as `PERMISSION_DENIED`, never as success.

Permission added: `android.permission.READ_PHONE_STATE` only — requested at
runtime, contextually, with a plain-language reason, and with an "Open app
settings" route once Android stops allowing re-prompts.

### 2.2 Backend — `core/sim_binding.py`, `core/truecaller.py`, `routes/sim_binding.py`

| Endpoint | Purpose |
|---|---|
| `POST /api/sim-binding/challenge` | Server nonce, 120 s TTL, single use, bound to the caller |
| `POST /api/sim-binding/verify` | Device SIM reading + nonce → records presence |
| `POST /api/sim-binding/number-proof` | Truecaller authorization code → server-side exchange |
| `GET  /api/sim-binding/status` | The server's own answer (the only truth the app trusts) |
| `POST /api/sim-binding/revalidate` | Force a re-check (support, SIM swap) |
| `POST /api/sim-binding/device-link/start` | Browser mints a QR/link code (3 min) |
| `POST /api/sim-binding/device-link/claim` | Verified phone approves it (24 h link) |
| `GET  /api/admin/sim-binding/overview` | Counts, policy and the security event tail |
| `PATCH /api/admin/sim-binding/policy` | Enforcement switches |
| `POST /api/admin/sim-binding/revalidate/{user_id}` | Admin forces a re-check |

Server-computed levels: `none` → `sim_presence` → `number_verified`, plus
`linked_device` for a browser riding on a verified phone. Presence expires
after 72 h so a resold or swapped handset cannot coast indefinitely.

Rejections by design: forged nonce, wrong nonce, replayed nonce, expired
nonce, another account's nonce, a `web` platform claiming a SIM reading, a
Truecaller code when no provider is configured, a Truecaller number that does
not match the account's number, a link code reused/expired/from another
account, and a policy level the platform cannot actually deliver.

### 2.3 Chat authorization

`core/sim_binding.chat_gate()` is enforced in `routes/chat.py` on **writes
only**: `POST /chat/threads`, `POST /chat/request`, `POST /chat/contact-support`,
`POST /chat/{thread_id}/messages`. It returns `403` with
`{code: "sim_verification_required", message, sim_status}` and the app turns
that into a "Verify now" prompt.

* Reading threads, history, media and starred messages is **never** gated — no
  conversation or message is lost or hidden.
* Admin/support accounts are never gated, otherwise a verification problem
  would be unreportable.
* Shopping, search, cart, checkout, payments, wallet, cashback, refunds,
  recharge, orders and all vendor/delivery tools are untouched — covered by
  explicit tests.

### 2.4 Website

No browser SIM reading is attempted (it is impossible, and claiming otherwise
would be the bug). `app/link-device.tsx` shows a QR + code on the browser; the
verified phone scans it with the existing camera module and approves. Codes
are single use, 3-minute, same-account only; the resulting browser link lasts
24 hours and then asks again.

## 3. Database migration plan

No migration is required and nothing existing is rewritten. Four new
collections are created lazily, with indexes built at startup
(`core/sim_binding.ensure_indexes()`):

| Collection | Contents | Index |
|---|---|---|
| `sim_bindings` | one row per user: level inputs, `carrier_fp`, timestamps | unique `user_id` |
| `sim_challenges` | single-use nonces | unique `id`, `user_id` |
| `sim_audit` | security events (no secrets) | `user_id + created_at` |
| `device_links` | browser link codes | unique `code` |

`users` gains nothing except, for an account with no number on file, the
number Truecaller itself confirmed. Rollback is simply switching
`enforce_chat` off; dropping the four collections leaves the app as it was.

**Retention:** `sim_challenges` rows are dead once used/expired and
`sim_audit` is an append-only evidence log — add a TTL (e.g. 180 days on
`sim_audit`, 1 day on `sim_challenges`) when the retention period is confirmed
with your legal review. Not set yet, because the right number is a policy
decision, not a technical one.

## 5. Free versus paid verification options

| Option | Cost | What it actually proves | Verdict |
|---|---|---|---|
| **Local SIM presence** (shipped) | Free, unlimited | A SIM/eSIM is present in this handset, and when it changes | Right tool for routine re-checks; **never** proof of number ownership |
| **Truecaller one-tap (OAuth 3.3)** | Was free; **commercial since 1 Apr 2026**, metered per successful production verification, no public price card — get a written quote from Truecaller sales | The number, confirmed by Truecaller's servers | Implemented and ready; cheapest realistic ownership proof, Android-only, strongest in India, needs the Truecaller app installed |
| **SMS OTP gateway** | ≈ ₹0.12–₹0.25 per SMS in India, every single re-verification | Number ownership | Avoided — this is exactly the recurring cost the brief set out to remove |
| **Carrier silent network auth** | Enterprise contracts, per-check pricing, per-operator onboarding | Strongest (network-level) | Not worth it at this stage |
| **Firebase Phone Auth** | Per-verification charges since 2023, India pricing on the Blaze plan | Number ownership via SMS | No advantage over a plain SMS gateway for this use case |
| **Truecaller missed-call fallback** | Account/market dependent | Number ownership without the Truecaller app | Only if Truecaller enables it for your account — confirm before promising it |

Nothing paid has been switched on. With no provider configured the server
**clamps** the requirement to `sim_presence` and the admin screen says so, so
the app can never silently claim a number was verified.

## 6. Legal applicability gaps and compliance checklist

This is a checklist to work through, **not** a compliance claim. No
regulatory conclusion is asserted.

* [ ] **DoT / telecom applicability.** Confirm with counsel whether Slangcart
      is in scope of any Department of Telecommunications SIM-binding
      expectation at all, or whether the obligation sits with the carrier.
      Enforcement can stay off until that answer exists — one switch.
* [ ] **DPDP Act 2023.** SIM presence relates to a person: record the purpose
      ("chat abuse prevention"), the retention period, and the lawful basis;
      add it to the privacy notice.
* [ ] **Purpose limitation.** The data collected is deliberately minimal —
      presence, slot count, eSIM flag, carrier network codes and a keyed
      fingerprint. Confirm nothing further is needed before adding anything.
* [ ] **Google Play Data safety.** Declare `READ_PHONE_STATE` and the "device
      or other IDs" section accurately. The app reads **state only**; say so.
      No restricted-permission declaration form applies (no SMS or call-log
      permission is requested).
* [ ] **Play policy on phone-state usage.** Keep the in-app explanation
      visible (already on the Verify SIM screen), because Play reviewers do
      look for the user-facing justification.
* [ ] **Truecaller contract.** Before go-live: written pricing, the data
      shared with Truecaller, and the user consent wording.
* [ ] **Accessibility of the fallback.** A user who refuses the permission
      keeps the whole shop; only chat is affected. Confirm that is the policy
      you want to publish.
* [ ] **Retention / erasure.** Wire `sim_bindings` and `sim_audit` into the
      existing account-deletion flow before enforcement is widened.

## 7. Staged release plan

1. **Now (done).** Code merged behind a server-controlled policy. Backend
   live; enforcement is honoured on every chat write.
2. **Build.** Publish → deploy → generate the Android build. First Kotlin
   compile happens here; check the build log.
3. **Device QA.** Real phones: single SIM, dual SIM, eSIM, no SIM, SIM
   removed while the app is open, permission denied once, permission denied
   permanently, airplane mode, roaming, a tablet, and the website.
4. **Watch before widening.** Admin → SIM binding shows bindings, confirmed
   numbers, re-check requests and rejected attempts. If `SIM_ABSENT` or
   `PERMISSION_DENIED` is unexpectedly common, flip `enforce_chat` off while
   it is investigated — no rebuild needed.
5. **Add number proof.** Supply the Truecaller Client ID, then raise
   `required_level` to `number_verified`. The clamp lifts automatically.
6. **Rollback.** `PATCH /api/admin/sim-binding/policy {"enforce_chat": false}`
   restores pre-change behaviour instantly. Chat history was never touched.

## 8. Honest limitations

* A local SIM check proves presence. It is **not** proof that the SIM, or the
  number on it, belongs to the Slangcart account. Every screen, the API
  response and the admin page say this in plain words.
* Android cannot reliably expose a SIM's own number without restricted
  permissions, and even then it is unreliable — so it is never used.
* `READ_PHONE_STATE` can be refused forever; those users keep the entire app
  except chat, and are given the settings route back.
* Cloned/"Dual App" instances, emulators and devices without telephony
  hardware cannot produce a meaningful reading and are reported as
  unsupported rather than failed.
* Play Integrity is still dormant; until its service account is configured, a
  determined attacker with a modified client is limited by the nonce, the
  rate limits and the audit trail, but not by hardware attestation.

## 9. Post-review hardening (same day, after independent testing)

An independent test pass found four real gaps. All are fixed and covered by
tests:

1. **A linked browser outlived the phone.** Once a browser was linked it kept
   chat for 24 h even after the phone reported no SIM, after a re-check was
   demanded or after a SIM swap. `record_device_check` and
   `require_revalidation` now clear `web_link_expires_at`, and the gate only
   honours a link while the phone itself still passes.
2. **Chat writes that skipped the gate.** Editing a message, accepting a chat
   request, "Ask this seller" on an order and asking a product question (which
   is copied into a seller chat) all went through ungated. All four are gated
   now.
3. **Device linking did nothing.** Verification is per account, so any browser
   session of a verified user already passed and `/link-device` declared
   itself "linked" seconds after showing a code, with no phone involved. The
   app now sends `X-Client-Platform` on every request (with a User-Agent
   fallback), the gate requires browsers to hold a live link, and the browser
   polls `GET /api/sim-binding/device-link/{code}` — the state of its OWN
   code — instead of the account's status.
4. **Silent failure on the website.** `Alert.alert` is a no-op on web, so a
   blocked send showed nothing. A shared `handleChatGateError` now uses
   `notify()` (works on web) and offers "Verify now" / "Link my phone" from
   the chat thread, the chat list and the service start-chat screen.

Also addressed: the unused `block_on_sim_absent` setting was removed rather
than left as dead config; taking the same SIM out and putting it back is no
longer counted as a swap (fingerprints are only compared between two PRESENT
readings); `/verify-sim` shows "Checking…" / "Sign in to verify" instead of a
misleading "SIM status unclear", and on the website no longer claims a SIM is
"active in this phone"; `/link-device` has a signed-out state instead of a raw
"Not authenticated"; and turning enforcement off in Admin now asks for
confirmation first.

**Still open and honest about it:** there is no hardware attestation yet, so a
logged-in script can still fetch a nonce and claim "SIM present". The hook is
in place — `POST /api/sim-binding/verify` accepts `play_integrity_token`, and
once `PLAY_INTEGRITY_ENABLED=1` plus the service-account JSON are configured
the token becomes **mandatory** and a failed verdict is rejected. The
browser-vs-app signal (`X-Client-Platform`) is a product rule, not a security
boundary: a modified client could claim to be the app, but only for an account
whose own phone already passed.

Tests after hardening: `test_sim_binding.py` **59 passed**, the independent
`test_iter103_sim_binding_independent.py` **13 passed**.

### Unrelated reporting bug found while regression-testing

The admin Excel "Receivables" sheet counted every open `vendor_outstanding`
row, including `return_refund` — a refund the SELLER still owes the shopper,
which the company never advanced. The workbook therefore read ₹4,030 against

## 10. Second review pass (iteration 104)

One **new** high-severity hole was found and closed, plus the remaining
rough edges:

* **A browser could approve its own link code.** It minted a code at
  `/device-link/start` and then claimed it in the same session, so chat opened
  with no phone involved. `/device-link/claim` now refuses browser callers
  outright — only a device that can actually read a SIM may vouch for one that
  cannot — and the attempt is written to the audit log as
  `browser_self_claim`.
* **Blocked-chat prompts that showed nothing on the website** are fixed in the
  remaining places: product-page "Ask vendor", My Orders "Ask this seller",
  chat message edit and chat image send all go through `handleChatGateError`
  now.
* **`/verify-sim` on the website** no longer says a SIM is "active in this
  phone": a verified account reads "Verified on your phone", with the
  reminder that the browser has no SIM of its own. The "Sign in to verify"
  flash on reload is gone — the screen checks whether a session token exists
  before deciding.
* **"[object Object]"** could appear when a check failed; the structured
  error's sentence is read out properly now.

Tests after this pass: `test_sim_binding.py` **64 passed** (5 new checks for
the self-claim hole), `test_iter104_sim_retest.py` **11 passed**,
`test_iter103_sim_binding_independent.py` **13 passed**.

### Workbook follow-up

The review also showed that a parked `return_refund` appeared **nowhere** in
the workbook: the "Vendor Outstanding" sheet is built from wallet
transactions, and parking a refund creates none. The Receivables sheet now
carries a clearly-labelled block *below* the total — "NOT a receivable —
refunds a seller still owes a shopper (the company never paid these)" — with
its own sub-total, so the money is visible and traceable without ever being
counted as company net worth. A leftover `TEST_v99` fixture row (₹30) that was
inflating live receivables was deleted.

### Known, accepted gaps

* **No hardware attestation yet.** A logged-in script can still fetch a nonce
  and claim "SIM present". The hook is wired (`play_integrity_token` becomes
  mandatory when `PLAY_INTEGRITY_ENABLED=1`), but the app does not yet send a
  token, so enabling that flag today would reject every real phone. Sending
  the token from the app is the next step before switching it on.
* **`X-Client-Platform` is a product rule, not a security boundary.** A
  modified client could claim to be the app — but only for an account whose
  own phone already passed a SIM check.
* A few chat-list controls still lack testIDs (cosmetic, test-only).
