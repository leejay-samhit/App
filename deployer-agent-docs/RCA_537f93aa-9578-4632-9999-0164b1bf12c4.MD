# Production RCA — network-pay-1 (run 537f93aa-9578-4632-9999-0164b1bf12c4)

DB: `network-pay-1-referral_ecom_db` (Mongo Atlas). Diagnosis is from live production logs + read-only DB inspection. **Nothing was changed.** These are live-data / timeout faults that cannot be reproduced in the eph sandbox (no prod secrets, no live Atlas, no data volume), so they are **diagnosed, not eph-reproduced** — tracebacks quoted verbatim below.

---

## SYMPTOM 1 — DELETE /api/admin/users/{id} → 500  (this is a TIMEOUT, not a logic exception)

Verbatim production traceback:
```
INFO: 172.68.155.222:0 - "DELETE /api/admin/users/bacabf71-be0a-4a25-9912-c9d089507fcc HTTP/1.1" 500 Internal Server Error
  File "/app/backend/core/idempotency.py", line 63, in dispatch
  File "/app/backend/server.py", line 3047, in admin_delete_user
    snap_info = await _take_snapshot(
  File "/app/backend/server.py", line 7501, in _take_snapshot
    await db.db_snapshot_chunks.delete_many({"snapshot_id": {"$in": expired_ids}})
pymongo.errors.NetworkTimeout: customer-apps-shard-00-01.8zw2qs.mongodb.net:27017: The read operation timed out
    raise NetworkTimeout(msg) from error
```

Root cause: it is a client-side **NetworkTimeout** (pymongo socket read timeout) inside `_take_snapshot`, specifically on the expired-chunk sweep `db_snapshot_chunks.delete_many({"snapshot_id": {"$in": expired_ids}})`. Timeout vs exception: **timeout** — the op ran until the driver's socket read deadline and gave up; no application-level exception was raised. The delete never completed → 500.

Why it times out (all three compound):
1. **`db_snapshot_chunks` has NO index on `snapshot_id`.** Confirmed via list_indexes — the collection carries only the default `_id_` index. The `delete_many({snapshot_id: {$in: [...]}})` is therefore a **full COLLSCAN** of a very large collection.
2. **The collection is huge / runaway.** `db_snapshots` = **1,160** snapshot rows. Each snapshot copies **every** collection (93 collections in this DB) into `db_snapshot_chunks`, so the chunk collection is on the order of 1,160 × 93 ≈ 100k+ chunk documents, each holding a serialized collection slice (e.g. `products` = **5,647** docs). A plain `count()` on `db_snapshot_chunks` **timed out** during this investigation — it is too large to even count inside the time limit. That is itself the smoking gun.
3. **Every admin delete writes a fresh full-DB snapshot first** (`kind="auto-pre-delete"`), and the handler also full-scans `db.tickets` to sweep orphan `ticket_messages`. So the collection grows by a full DB copy on every delete, which makes both the write and the unindexed expired-chunk sweep progressively slower until they cross the socket timeout. The feature is self-amplifying.

## SYMPTOM 2 — POST /api/auth/register → 500  (NOT the email index — it is PHONE)

Verbatim production traceback (identical shape for the register 500 and the recurring admin 500s):
```
INFO: 104.22.171.14:0 - "POST /api/auth/register HTTP/1.1" 500 Internal Server Error
pymongo.errors.DuplicateKeyError: E11000 duplicate key error collection:
  network-pay-1-referral_ecom_db.users index: uniq_user_phone
  dup key: { phone: "9154735888" }
  ... 'keyPattern': {'phone': 1}, 'keyValue': {'phone': '9154735888'} ...
```

Root cause: a **pymongo `DuplicateKeyError` (E11000) on the `uniq_user_phone` index (`{phone:1}`)** — a second account registering with an already-used phone number. It is **not** a validation error and **not** the `users.email` index. The handler inserts without catching `DuplicateKeyError`, so the collision surfaces as an unhandled 500 instead of a clean 409/400 "phone already registered".

Important correction to the preview hypothesis: the email concern is **already resolved on production** — see Q3. The live collisions are all on **phone**, not email.

## ANSWERS TO THE SPECIFIC QUESTIONS

**Q1 — DELETE traceback + duration (timeout vs exception):** TIMEOUT. `pymongo.errors.NetworkTimeout: ...mongodb.net:27017: The read operation timed out`, raised from `_take_snapshot` (server.py:7501) via `admin_delete_user` (server.py:3047), on `db_snapshot_chunks.delete_many({snapshot_id:{$in:...}})`. It ran to the driver's socket read deadline (no explicit maxTimeMS on this op) rather than throwing a logic error.

**Q2 — register traceback (E11000 vs validation vs other):** `pymongo.errors.DuplicateKeyError` E11000 on index **`uniq_user_phone`** (`{phone:1}`), dup key `phone:"9154735888"`. Not a validation error, not email.

**Q3 — current production `users` indexes (6):**
| name | key | unique | partialFilterExpression |
|---|---|---|---|
| `_id_` | `{_id:1}` | — | — |
| `referral_code_1` | `{referral_code:1}` | **yes** | **none** (plain unique) |
| `sponsor_id_1` | `{sponsor_id:1}` | no | — |
| `service_location_2dsphere` | `{service_location:"2dsphere"}` | no | — |
| `uniq_user_phone` | `{phone:1}` | **yes** | **`{phone:{$gt:"", $type:"string"}}`** (partial) |
| `email_1` | `{email:1}` | **yes** | **`{email:{$gt:"", $type:"string"}}`** (partial) |

=> **The email unique index on production is ALREADY a PARTIAL index.** The old non-partial `users.email` unique index is **not** present on the live DB. **No email index migration is required.** Mobile-only accounts with no email will NOT collide on email. Note `uniq_user_phone` is likewise partial (so missing phone is fine), but a **duplicate non-empty phone still (correctly) collides** — that is the register/PATCH 500.

**Q4 — Atlas read timeouts / MaxTimeMSExpired + doc counts:** YES, present on production:
- Client-side `NetworkTimeout` on `db_snapshot_chunks.delete_many` (the DELETE 500 above).
- Server-side `MaxTimeMSExpired` (code 50): `2026-11-14 14:38:10 - backup - ERROR - backup stream: product_image_files failed after some rows: Executor error ... operation exceeded time limit ... 'codeName':'MaxTimeMSExpired'`.
- Counts: `products` = **5,647**; `db_snapshots` = **1,160**; `db_snapshot_chunks` = **count() TIMED OUT** (collection too large to count within the limit — diagnostic of the bloat).

**Q5 — other recurring 5xx:**
- **`PATCH /api/admin/users/{id}` → 500 (recurring, many times):** same `uniq_user_phone` DuplicateKeyError, raised at `admin_update_user` server.py:**2917**. Admins editing a user and setting a phone that already exists → unhandled E11000 → 500. Same class as register.
- **nginx `connect() failed (111: Connection refused) ... upstream 127.0.0.1:8001 /health`:** intermittent, around worker/pod startup; `/health` otherwise returns 200. Transient startup race, low severity — flag, not a user-facing bug.
- `routes.geo` `429 Too many requests` from nominatim.openstreetmap.org — external rate-limit WARNING (not a 5xx), but recurring and worth backing off / caching.

## SUGGESTED FIXES (for E1 to apply in source — nothing applied here)

**A. Symptom 1 (DELETE timeout) — backend/server.py `_take_snapshot` / `admin_delete_user`:**
1. (DB, one-time) Create an index on the sweep key so the expired-chunk delete stops full-scanning: `db.db_snapshot_chunks.create_index("snapshot_id")` (and consider `{snapshot_id:1, collection:1, seq:1}`). The user can run this one-time via the Deployment Panel → Database. Add the same `create_index` to the app's startup index-ensure block so it is guaranteed on every deploy.
2. Stop the runaway growth: the `auto-pre-delete` snapshot copies **every** collection on **every** admin delete (1,160 snapshots already). Reconsider scope — e.g. only snapshot the user-scoped docs being deleted, cap retention aggressively, and **never** let the snapshot include `db_snapshot_chunks`/`db_snapshots` themselves. Purge the existing backlog (retention sweep) as a one-time cleanup.
3. Make the slow ops bounded instead of hanging the request: add an explicit `maxTimeMS`/`maxTimeMS` on the snapshot writes + the `delete_many`, and move the whole snapshot to a background task so the delete endpoint returns fast. Replace the full `db.tickets` scan with an indexed query on the deleted user's id.

**B. Symptom 2 (register) + PATCH admin update — catch the collision:**
- Wrap the `users` insert in `register` (server.py ~230-330) and the update in `admin_update_user` (server.py:2917) in `try/except pymongo.errors.DuplicateKeyError` and return **HTTP 409** with a clear "phone already registered" (inspect `e.details['keyPattern']` to say phone vs email vs referral_code). This converts all of these 500s into correct client errors. No DB migration needed for this symptom.
- Note: `referral_code_1` is a **plain** unique index (no partial filter). If any flow can insert a user with empty/duplicate `referral_code`, that will also E11000 — worth the same guard.

**Reproduction note:** not reproduced in the eph sandbox — both faults depend on live Atlas and its data volume (the timeout needs the 1,160-snapshot bloat; the E11000 needs the existing `phone:9154735888` doc), which the sandbox cannot host. Findings are taken directly from production logs and read-only DB inspection quoted above.
